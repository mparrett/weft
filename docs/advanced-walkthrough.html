weft, past the basics

Two repositories, several agents, and a week of drift — merges, blast radius, routes, inferred claims, retractions, and what the tool refuses to do.

Getting started covers the loop: assert, connect, ask what is startable, record state. This picks up where it stops, on the graph you actually end up with once more than one person and more than one repository are writing to it. Every command below was run in order against an empty store and the output is what it printed — including the three commands near the end that fail on purpose.

The scenario. Batch export v2 spans two repos. In acme/api: an epic, a spec, an N+1 bug already filed as #412, and the task to extract the report query. In acme/web: the progress panel that cannot ship before the spec settles, and someone else's rate-limit PR that touches the same middleware. An agent has been reading the repo and asserting what it finds.

1. Two repos, one graph

There is one store, not one per repository. The namespace is a field on the node, so a node in acme/web can depend on one in acme/api with no special case anywhere.

$ weft ns
acme/api        (WEFT_NS)

$ weft add "batch export v2" --kind task
0576d6a  batch export v2  [acme/api]

$ weft add "batch export spec" --kind spec --ref file:docs/export.md
8baa619  batch export spec  [acme/api]

$ weft add "N+1 in report generation" --kind bug --ref gh:acme/api#412
6413156  N+1 in report generation  [acme/api]

$ weft add "extract report query" --kind task
2d7e850  extract report query  [acme/api]

$ weft add "export progress panel" --kind task --ns acme/web
8aa903a  export progress panel  [acme/web]

$ weft add "rate-limit middleware" --kind pr --ns acme/web --source observed
6c66798  rate-limit middleware  [acme/web]

Every query defaults to the current namespace. --all-ns is how you see the whole thing, and it prints the namespace column that the single-namespace listing leaves out.

$ weft ls --all-ns
0576d6a  acme/api  task  batch export v2
8baa619  acme/api  spec  batch export spec
6413156  acme/api  bug   N+1 in report generation
2d7e850  acme/api  task  extract report query
8aa903a  acme/web  task  export progress panel
6c66798  acme/web  pr    rate-limit middleware
The last one is somebody else's PR. --source observed says weft is recording something that exists in the world rather than asserting new work. The three values — asserted, observed, inferred — are what let you read a graph that is roughly half inference without having to trust all of it equally.

2. When two writers assert the same work

This is the normal case with agents, not an edge case. Node ids are event hashes, so two assertions of the same work are two nodes — deciding they are the same is a judgement, and weft makes you make it. There is a way to avoid the problem and a way to fix it afterwards.

--if-absent is the avoidance: reuse the earliest live node with this exact title in this namespace, otherwise create one. The write becomes idempotent, which is what a scheduled job or a re-running agent needs.

$ weft add "batch export spec" --kind spec --if-absent
8baa619  batch export spec  [acme/api]   # the id from step 1, not a new one

It only matches an exact title, so it does nothing for the case that actually happens: an agent phrases it differently.

$ weft add "extract the report query" --kind task --source inferred
e277ad7  extract the report query  [acme/api]

$ weft merge 2d7e850 e277ad7
2d7e850 merged e277ad7

The first argument survives. The second keeps resolving — anything already holding the merged id, a script, a branch name, an agent halfway through a task, lands on the survivor rather than on nothing.

$ weft show e277ad7
2d7e850  task  extract report query
  ns     acme/api
  state  open
  source asserted, per user:you
  age    created just now, touched just now
  merged e277ad7  extract the report query
There is no merge --undo, and the absence is deliberate. Undoing a merge is not bookkeeping: events that landed on the survivor afterwards would have to go back to the node they named, which needs replay. Merge when you are sure. EVENTS.md §3.7 records the reasoning.

3. A blocker in another repository

$ weft link 2d7e850 depends-on 8baa619
2d7e850 depends-on 8baa619

$ weft link 2d7e850 depends-on 6413156
2d7e850 depends-on 6413156

$ weft link 8aa903a depends-on 8baa619
8aa903a depends-on 8baa619

$ weft link 2d7e850 part-of 0576d6a
2d7e850 part-of 0576d6a

$ weft link 8aa903a part-of 0576d6a
8aa903a part-of 0576d6a

$ weft link 8aa903a conflicts-with 6c66798 --source inferred
8aa903a conflicts-with 6c66798

The third of those crosses a repository boundary, and the fourth conflict edge is a guess — the agent noticed both touch the same middleware and said so, marked as a guess. Now ask the web repo what it can start:

$ weft ls --ready --ns acme/web
6c66798  pr  rate-limit middleware

$ weft why 8aa903a
8aa903a  export progress panel

blocked by

  8baa619  spec  batch export spec  [acme/api]
A namespace filter selects which nodes come back, never how far the walk goes. The panel is in acme/web and its blocker is not, so a tool that filtered before walking would have called it ready. That is the failure mode worth knowing about: it does not error, it just quietly tells you to start something you cannot finish. why names the blocker's namespace for the same reason (SPEC.md §5).
$ weft ls --blocked --all-ns
2d7e850  acme/api  task  extract report query
8aa903a  acme/web  task  export progress panel

4. Blast radius, before you touch anything

why looks down at what is stopping you. rdeps looks up at who is waiting on you — the question to ask before you change a spec, retitle a task, or mark something dropped.

$ weft rdeps 8baa619
2d7e850  task  extract report query
8aa903a  task  export progress panel  [acme/web]
via: depends-on (the default; --via walks other kinds)

It walks depends-on transitively by default. --via walks a different kind — part-of turns the same command into "what is in this epic" without a container type existing anywhere in the model. A widened walk lists what is reachable rather than what waits, so each row names the relation it was reached through:

$ weft rdeps 0576d6a --via part-of
2d7e850  task  extract report query  (part of)
8aa903a  task  export progress panel  (part of)  [acme/web]
via: part-of

$ weft rdeps 6413156 --depth 1
2d7e850  task  extract report query
via: depends-on (the default; --via walks other kinds)
Every traversal prints the kinds it walked. An empty result and an empty result for the kind you forgot to ask about look identical otherwise, and the second one is a wrong answer wearing the costume of a right one.

5. How are these two things related?

Someone asks whether the panel is affected by bug #412. They are in different repos with nothing obviously between them. path answers with the route:

$ weft path 8aa903a 6413156
8aa903a  export progress panel
  depends on 8baa619  batch export spec  [acme/api]
  blocks 2d7e850  extract report query  [acme/api]
  depends on 6413156  N+1 in report generation  [acme/api]
via: depends-on, conflicts-with, part-of, supersedes, derived-from, same-as (all kinds; --via restricts; either direction; --dir restricts)

Read the middle hop: the route goes up the spec and back down through the query task. By default path crosses edges in either direction, because "how do these relate" is rarely a question about arrow direction. --dir out asks the stricter question — does a lead to b, following arrows only:

$ weft path 2d7e850 0576d6a --dir out --via part-of
2d7e850  extract report query
  part of 0576d6a  batch export v2
via: part-of (forwards only)

$ weft path 0576d6a 2d7e850 --dir out --via part-of
no known route from 0576d6a to 2d7e850
via: part-of (forwards only)

The same two nodes, the same edge, opposite answers — which is the point of having the flag. Note the wording: no known route. A graph is a record of what somebody wrote down, never a claim about the world.

6. Claims about other people, and claims nobody came back to

Claims are advisory: they do not lock, and two live claims on one node is a reported condition rather than an error. That is what makes it safe to record a claim on someone else's behalf — an inference from a PR being open, which may simply be wrong.

$ weft claim 6413156 --holder user:dana --source inferred --ttl 2s --note "PR open, no reviewer"
6413156 claimed by user:dana

$ weft show 6413156
6413156  bug  N+1 in report generation
  ns     acme/api
  state  open
  source asserted, per user:you
  age    created just now, touched just now
  refs   gh:acme/api#412

  claimed by
    user:dana  (inferred, per user:you)  PR open, no reviewer

  blocks
    2d7e850  task  extract report query
(inferred, per user:you) is the whole feature. Dana never said this. Anyone reading the graph can see that it is your guess about Dana rather than Dana's word, which is the difference between a note that gets trusted and one that gets ignored.

Claims expire — the default TTL is seven days. The two-second TTL above is so this page can show you the sweep without a week passing:

$ sleep 3

$ weft ls --stale --all-ns
6413156  acme/api  bug  N+1 in report generation

--stale lists nodes whose every claim has expired: work somebody picked up and never came back to. It is the one query that finds the thing nobody will tell you about. When a claim genuinely should outlive the TTL, say so rather than picking a big number:

$ weft claim 2d7e850 --no-expiry --note "long-running"
2d7e850 claimed by user:you

$ weft ls --mine
2d7e850  task  extract report query

$ weft release 2d7e850
2d7e850 released by user:you
release --holder drops someone else's claim — for when the inference above turns out to be wrong. Releasing a claim that is already gone is exit 0 and a plain sentence, not an error, so a cleanup script does not need to check first.

7. Retracting and correcting

The log is append-only, which is not the same as unchangeable. Every retraction is a new event that says what changed; nothing is rewritten, and the history stays readable.

$ weft unlink 8aa903a conflicts-with 6c66798
unlinked 8aa903a conflicts-with 6c66798

$ weft ref add 2d7e850 branch:fix/report-query
2d7e850 bound to branch:fix/report-query

$ weft ref rm 2d7e850 branch:fix/report-query
2d7e850 no longer bound to branch:fix/report-query

State moves the same way, and it moves back. Marking the spec done frees the panel; undoing it puts the panel back where it was.

$ weft done 8baa619
8baa619 done

$ weft ls --ready --ns acme/web
8aa903a  task  export progress panel
6c66798  pr    rate-limit middleware

$ weft done 8baa619 --undo
8baa619 open

$ weft drop 6c66798
6c66798 dropped

$ weft ls --all-ns
0576d6a  acme/api  task  batch export v2
8baa619  acme/api  spec  batch export spec
6413156  acme/api  bug   N+1 in report generation
2d7e850  acme/api  task  extract report query
8aa903a  acme/web  task  export progress panel
6c66798  acme/web  pr    rate-limit middleware  (dropped)
drop is not delete. The node stays listed and annotated, because "we decided not to do this" is information, and the edges pointing at it are information too. drop --undo exists for the same reason done --undo does: a wrong state recorded quickly beats a right state recorded never.

8. What weft refuses, and how it says so

Three commands here fail on purpose. Exit codes are a stable contract because agents branch on them.

$ weft link 8baa619 depends-on 2d7e850
weft: this edge would create a depends-on cycle:

    2d7e850  extract report query
  → 8baa619  batch export spec
  → 2d7e850  extract report query
# exit 5

$ weft show deadbee
weft: no node matches "deadbee"
# exit 2

$ weft link 2d7e850 blocks 8baa619
weft link: unknown edge kind "blocks" (want one of: depends-on, conflicts-with, part-of, supersedes, derived-from, same-as)
# exit 1

The cycle rejection prints the cycle it would have made, not the word "invalid" — the fix is usually to reverse one of those edges, and you cannot pick which without seeing them. Acyclicity is enforced per edge kind: depends-on must stay a DAG, while conflicts-with is symmetric and cyclic by nature, so a global check would reject valid data.

exitmeanswhat a caller should do
0success—
1usage: unknown command, bad flag, missing argumentfix the call
2no node matchesthe id is wrong or the node was never created
4the prefix is ambiguousretry with more characters
5rejected: the write is well-formed but not allowedread the message; do not retry
6the store could not be read or writtenstop
7a shell-out failed — gh missing, not authenticated, refusednot weft's fault; retry or re-auth
Exit 7 exists so it is not exit 6. Folded together, "GitHub said no" would read as "your log is corrupt", which sends you to entirely the wrong place at the worst possible moment.

9. Seeding from what already exists

Everything above was typed. Real graphs start from a repository, and import shells out to gh to bind nodes to issues and pull requests.

$ weft import gh acme/api --merged-since 30d --limit 50

Merged pull requests come in as done, which matters more than it sounds: on a graph where nothing is done, every node's nearest open blocker is one hop away and why and ls --ready look broken. Re-running an import appends nothing when nothing upstream changed — byte for byte, not merely "no duplicate node", so a scheduled sync does not grow the log forever.

Upstream is cached, never authoritative. An import records what GitHub said and when, as an observation with an age. The node's own title and state stay weft's, because ready, blocked and why all key off state — a helpful sync from upstream would silently rewrite your frontier. show renders observations with their age for the same reason: stale data shown as current is worse than no data.

10. Driving it from a script or an agent

Every command takes --json, and the filters compose — this is how an agent asks a specific question instead of listing everything and reasoning about it.

$ weft ls --ready --all-ns --kind task
0576d6a  acme/api  task  batch export v2

$ weft ls --recent --since 72h --all-ns
6c66798  acme/web  pr    rate-limit middleware  (dropped)
8baa619  acme/api  spec  batch export spec
2d7e850  acme/api  task  extract report query
8aa903a  acme/web  task  export progress panel
6413156  acme/api  bug   N+1 in report generation
0576d6a  acme/api  task  batch export v2

The JSON forms carry more than the text does. why --json returns the whole blocking path rather than the nearest hop, plus known, which is how a caller tells "nothing is blocking this" from "nothing recorded is blocking this":

$ weft why 2d7e850 --json
{
  "blockers": [
    {
      "id": "8baa61906bb10a3927481edc5d8800bd94d27206a7846576b4d1a18dc0573b1d",
      "title": "batch export spec",
      "kind": "spec",
      "known": true,
      "path": [
        "2d7e85075ac29dd7e9eb3484db9fa51bcf7f4598e9af3891093a78836405baab",
        "8baa61906bb10a3927481edc5d8800bd94d27206a7846576b4d1a18dc0573b1d"
      ],
      "gates": 0
    },
    ...

When something surprises you, ask which store you are talking to before anything else. It creates nothing:

$ weft env
version   0.1.0
store     /Users/you/.weft            (default)
log       /Users/you/.weft/log.jsonl  (25 events, 6.9 KB)
actor     user:you                    (git config user.email)
ns        acme/api                    (WEFT_NS)

And for the artifacts that leave your machine:

$ weft view --only-ns acme/api
$ tools/weft-range-context.py -C ~/src/acme-api origin/main HEAD > ctx.md
--only-ns is what makes the page safe to send: the other namespaces are not in the file, and an edge that leaves the scope keeps only a stub of its far end. Add --self-contained to inline the renderer, so the file draws on a machine with no network. weft-range-context.py answers the other direction: given a commit range, what in the graph does it touch, what is still blocking it, and who is waiting on it — the thing a diff cannot tell you.

11. Where to go next

  • weft help agent — the orientation snippet to paste into a project's CLAUDE.md. It ships inside the binary, so it cannot drift from it.
  • SPEC.md — the data model and query semantics, with an appendix recording the prior art behind each decision.
  • EVENTS.md — the log format. Normative, and it wins on any conflict with SPEC.
  • getting-started.html — the ten-minute version, if you arrived here first.
All of it is one append-only JSONL file. The merge, the retraction, the expired claim and the inference are events in the same log, and the graph is a fold over them. That is where history, audit and multi-writer support come from — and why the log, not the binary, is the contract.
